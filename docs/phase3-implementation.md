# Phase 3 implementation: asset registry and primary issuance

Requirements: [phase3-requirements.md](spec/phase3-requirements.md), including user decisions D1–D4. Where those differ from [spec-v1](spec/spec-v1.md), they govern. Generated by Claude Code (Opus 5.5) on 23 October 2026. Commits are prefixed `ai:`.

## Contracts

### AssetFactory (`contracts/AssetFactory.sol`)

| Function | Caller | Reverts if | Event | Traces to |
|---|---|---|---|---|
| `constructor(admin_)` | deployer | `admin_ == 0` (`InvalidAdmin`) | — | spec-v1 §4 |
| `authorizeIssuer(addr)` | admin | not admin (`NotAdmin`); `addr == 0`; already authorised | `IssuerAuthorised` | Phase 3 §3.1, spec-v1 §5 |
| `revokeIssuer(addr)` | admin | not admin; not authorised | `IssuerRevoked` | Phase 3 §3.1, spec-v1 §5 note |
| `createAsset(name, symbol, description, assetType, totalSupply, unitPriceWei)` | authorised issuer | not authorised; supply 0; price 0; bad enum value | `AssetCreated(assetId, token, sale, issuer)` | Phase 3 §3.1, D2 |
| `getAsset(assetId)` | anyone | unknown ID (`AssetNotFound`) | — | Phase 3 §3.1 |
| `getAssetCount()` | anyone | — | — | Phase 3 §3.1 |

- `assetId` is the registry index, starting at 0.
- `AssetType` is `{ RealWorld, Digital }` (D2).
- `authorisedIssuers` and `tokenToSale` keep their spec-v1 names. spec-v1's `address[] assets` is replaced by `getAsset` / `getAssetCount`.
- The factory is never granted a role on the tokens it deploys. Supply and both token roles go to the calling issuer, so the issuer must whitelist and fund the sale themselves (Phase 3 §3.3).
- Revoking an issuer only blocks future `createAsset` calls. Contracts already deployed keep working (spec-v1 §5 note; tested).

### AssetSale (`contracts/AssetSale.sol`)

| Function | Caller | Reverts if | Event | Traces to |
|---|---|---|---|---|
| `allocate(amount)` | issuer | not issuer; closed; amount 0; sale not whitelisted; no allowance; insufficient balance | `Allocated` | Phase 3 §3.3, spec-v1 §5 |
| `buyTokens(quantity)` payable | whitelisted investor | closed; quantity 0; buyer not whitelisted; quantity > inventory; `msg.value != quantity * pricePerToken` | `Purchased(buyer, quantity, paid)` | Phase 3 §3.2 |
| `withdrawProceeds()` | issuer | not issuer; nothing owed; ETH send fails | `ProceedsWithdrawn` | Phase 3 §3.4, spec-v1 §4 reentrancy and invariant 8 |
| `closeSale()` | issuer | not issuer; already closed | `SaleClosed` | Phase 3 §3.4, D3 |
| `recoverUnsoldTokens()` | issuer | not issuer; sale open; no inventory | `UnsoldTokensRecovered` | Phase 3 §3.4, D3 |
| `availableTokens()` | anyone | — | — | spec-v1 §7 (investor dashboard) |

- `assetToken`, `issuer` and `pricePerToken` are `immutable`, so there is no way to change the price after creation (Phase 3 §3.3; tested).
- `assetToken` is typed `AssetToken` rather than the brief's `IERC20` because `buyTokens` must read `isWhitelisted`. The ABI is the same either way: an address getter.
- **Reentrancy (invariant 8):** proceeds are tracked in `unclaimedProceeds`. `withdrawProceeds` zeroes it before the `.call`.
- **No `receive`/`fallback`:** plain ETH sends revert. *Corrected after audit-1 F-08:* the original note claimed that ETH could therefore only arrive through `buyTokens` and invariant 3 held. That is false. `selfdestruct` and coinbase rewards can force ETH into the contract, where it was stuck. Fixed in AUD-007.
- `SafeERC20` is used for token movements, which is standard practice. AssetToken reverts on failure anyway.

## Demo (completion criteria)

`npx hardhat run scripts/setupDemo.ts --network hardhatMainnet` runs these steps:

1. deploy the factory
2. authorise the issuer
3. create CPT and DLP
4. whitelist the CPT sale and the investor
5. allocate 5,000 CPT
6. investor buys 100 CPT for 0.1 ETH
7. print the balances: issuer 5,000 / sale 4,900 / investor 100 / supply 10,000 / sale ETH 0.1

Output: [setupDemo.log](evidence/phase3/setupDemo.log).

`scripts/deploy.ts` deploys the factory. On HTTP networks it also writes `frontend/src/config/addresses.json`. It has only been run in-process ([deploy-local.log](evidence/phase3/deploy-local.log)).

## AI mistakes observed in this session

These were caught before commit, in test code or test design, so no AUD issue was filed. Each is stated from what the session shows.

1. **Unsupported matcher chaining.** The first test draft chained `.emit(...).and.to.changeTokenBalances(...)`. The Hardhat 3 chai-matchers README lists `changeTokenBalances` as non-chainable. The run failed with an unhandled `ProviderError` ("maxFeePerGas … too low"). Both occurrences were split into separate `expect`s.
2. **An invariant 8 test that could not fail.** The first draft only checked that the re-entrant call did not succeed. That check passes even if the contract violates CEI: the sale only ever holds the ETH it owes, so a second payout fails for lack of funds whatever the ordering. This was found by reasoning, not by running the mutant against the weak test. It was fixed by asserting the balance seen mid-payout, then confirmed with the mutation above.

## Known limitations and open points

- **Factory size:** 22,557 bytes deployed with the optimiser off, against the EIP-170 limit of 24,576 ([bytecode-sizes.txt](evidence/phase3/bytecode-sizes.txt)). It fits, but little headroom remains. The `production` build profile enables the optimiser.
- **Standalone sales:** a standalone `AssetSale` can be deployed by anyone against any token. Its constructor does not check `issuer_ == token.issuer()`. The factory registry is the source of truth for legitimate sales. Such a contract can only sell inventory that its own "issuer" approved to it.
- **Whitelist dependencies:** the issuer can de-whitelist the sale contract, which halts buying and recovery. The issuer can also de-whitelist themselves, which blocks recovery. *Corrected after audit-1 F-05:* the original note said "both can be undone by the issuer, who holds `COMPLIANCE_ROLE`". That assumed the issuer keeps the role, but the issuer could renounce it or have it revoked, which permanently locks the inventory. Fixed in AUD-006.
- **Sepolia demo:** `setupDemo.ts` needs three signers, but `hardhat.config.ts` configures one `PRIVATE_KEY` for Sepolia. Multi-wallet testnet runs belong to Phase 5.
- **`localhost` network:** *corrected after audit-1 F-16.* The original note said no `localhost` network existed. That is wrong: Hardhat 3 adds `localhost` at `http://localhost:8545` when the config omits it (`network-manager/hook-handlers/config.js`). `deploy.ts --network localhost` against `npx hardhat node` will therefore write `addresses.json`.
- **Out of scope:** pause, freeze and forced transfer (spec-v1 §4) are still not implemented, pending a team decision. AUD-001 stays open for them.
- **`scripts/evidence.sh` was not run** during Phase 3, because it required `forge`. It has since been ported to Hardhat 3 (audit-1 F-13).
- **The invariant-1 test checked a weaker property than its name** (audit-1 F-04). It never exercised a revocation, and since Phase 2 a revoked holder legitimately keeps their balance. Addressed in AUD-005.
