# ERC-3643-inspired Lite — implementation specification

Governing request: [Enhancement C](spec/erc3643-lite-requirements.md). This additive specification supersedes the legacy whitelist rules only for new regulated assets. Existing deployments are immutable. No claims of full ERC-3643 compliance or real legal qualification.

## A. Identity (§3)
Each regulated asset has its own registry. The platform administrator manages trusted attestors and can revoke credentials; only trusted attestors register/update credentials. Neither role can attest its own wallet. Updating requires an existing record and preserves its opaque identity ID; it replaces attributes and attestor and clears revocation. No deletion or accidental registration overwrite. Admin is not automatically an attestor. Original registry administrator cannot relinquish its recovery authority. Supported ISO numeric demo countries are 702 Singapore, 840 United States, 356 India; all others are explicitly unsupported, not assumed invalid ISO codes. Synthetic identifiers only. Verification requires KYC, live expiry, no revocation and a currently trusted attestor. Role changes emit explicit attestor events.

## B. Per-asset policy (§4)
Issuer is immutable policy administrator. Country allowlist defaults to deny; positive maximum defaults to supplied policy; zero means no investor holdings permitted (not unlimited). Accreditation is independent. Country/accreditation apply to the recipient; ordinary sender must have valid identity. Reducing a cap does not confiscate holdings or prevent sending out. Self-transfers/zero transfers cannot increase holdings and do not fail merely because a lowered cap is below the unchanged balance. They still check both identities and recipient policy. Policy is bound once by its constructor-appointed deployer, atomically during creation. No mutable validation references, arbitrary policy modules or callback writes.

## C. Token and custody (§5–6)
Fixed supply minted once via OpenZeppelin ERC20 constructor path; zero decimals. No external mint/burn, forced transfers, recovery or freeze. `paused()` is a compatibility getter returning false in core MVP. `isWhitelisted` is a compatibility getter derived from identity plus recipient country/accreditation (without amount/holdings); no boolean whitelist setter. Actual movements enforce identical `transferStatus` logic inside `_update`. Codes: 0 allowed, 1 invalid sender identity, 2 invalid recipient identity, 3 restricted country, 4 accreditation required, 5 holding limit, 7 insufficient balance, 8 zero endpoint. Delegated transfers also need ERC20 allowance; preflight does not promise allowance or future execution.

Issuer, exact factory-created sale and registered subscription escrows are permanent operational classes. They bypass only investor identity/country/accreditation/holding checks. Recipient investors always face full checks. There is deliberately no removal or arbitrary exemption API, so an administrator cannot revoke escrow authorization and strand claims. Registering a subscription requires issuer permission, a one-time platform-selected SubscriptionFactory linked to this asset registry, its `isOffering` membership, and matching token and issuer. No EOA or arbitrary contract registration. Existing offering accounting remains authoritative for custody; no admin seizure.

## D. Deployment (§7)
`RegulatedAssetFactory` extends the existing AssetFactory registry and still supports legacy creation. A constructor-deployed immutable helper deploys registry, policy, token and sale; its only caller is that factory. This keeps EIP-170 runtime sizes bounded. Platform admin is identity admin, issuer is policy admin. Helper has only consumed one-time binding powers and no identity or policy role. New regulated factory and subscription registry are local deployments; old frontend deployment config is not overwritten without an explicit deployment command. Metadata maps asset IDs to registry/policy addresses; legacy assets return zero addresses. One-time subscription-factory selection is trusted platform administration and validated for matching asset registry; deploy scripts use the audited implementation.

## E. Financial integration (§8)
Sales check eligibility and execute atomic token transfer; failed delivery rolls back ETH/proceeds. Commitments check current identity, country and accreditation, but reserve no wallet capacity. Finalization/allocation/refunds are unchanged. Claims recheck identity/policy/holdings. Blocked allocations stay reserved indefinitely; renewal, moving eligible existing holdings out, or issuer policy update permits eventual claim. Refunds require no asset identity. No automatic allocation reduction, forfeiture or claim deadline.

## F. Browser, verification and evidence (§9–15)
The existing issuance form offers regulated mode when the configured factory supports it. A Compliance route provides role-controlled attestor/credential/policy administration, connected-wallet status and real on-chain preflight. Public reads refresh after receipts and wallet session changes; stale account data is cleared. Existing sale/transfer/claim sends preflight regulated delivery. ABI generation and local deployment/demo scripts are reproducible. Tests cover identities, roles, boundaries, independent policies, custody, direct/delegated transfers, sales, subscriptions and refunds. Documentation records actual results and limitations, not hypothetical findings.
