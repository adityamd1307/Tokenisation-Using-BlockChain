# Project rules for Claude Code

This repo is graded on two things: the dApp, and how well we audit the code AI tools wrote for it. The process below exists so every claim in our AI Audit Report has evidence behind it. Follow it even when it feels slower.

## Before writing any code

- Read `docs/spec/spec-v1.md` first.
- If it still contains `TODO(decision)` markers, the spec is not frozen. Do not write contract code. Say which decisions are still open and stop.
- Every function you write must trace to a section of the spec. If the spec is silent or ambiguous on something you need, stop and ask. Do not invent requirements.

## Branches and tags

- Never commit to, rebase, or rewrite the `ai-baseline` branch, or move the `spec-v0` or `ai-baseline` tags.
- Never amend published commits or force-push.

## When a bug, vulnerability or spec gap is found

1. Run `scripts/new-issue.sh "<short title>"`. This creates `docs/issues/AUD-NNN-*.md`.
2. Write a regression test that FAILS on the current code. Commit it alone as `test(AUD-NNN): ...`.
3. Run `scripts/evidence.sh AUD-NNN-before`.
4. Fix the code. Commit as `fix(AUD-NNN): ...`.
5. Run `scripts/evidence.sh AUD-NNN-after`.
6. Fill in all four sections of the issue file. Do not set Status to fixed without both evidence runs.

In "Why the AI made the mistake", only state what the transcript or code shows. If you are guessing, start the line with `Hypothesis:`.

## Secrets

- Never read `.env` or print private keys, RPC keys or API keys. AI transcripts in this repo are committed to git.
- Only testnet burner wallets are used in this project.

## Commit message prefixes

| Prefix | Use for |
|---|---|
| `ai:` | Code generated by an AI tool and committed with little or no human change |
| `human:` | Code written or substantially rewritten by a person |
| `test(AUD-NNN):` | Regression test for an issue |
| `fix(AUD-NNN):` | Fix for an issue |
| `docs:` | Spec, report, issue files |
| `evidence:` | Evidence runs, testnet logs |
| `chore:` | Tooling and config |

## Rules learned from audit findings

Append a rule here each time an audit finding shows the AI making a mistake it could repeat. Every rule must cite the issue it came from. This section is part of our specification engineering evidence, so never delete old rules; mark them superseded instead.

- AUD-004: A whitelist mapping alone does not restrict ERC-20 movement. Enforce sender and recipient eligibility in OpenZeppelin's transfer hook and execute a direct-transfer regression; skipped tests are not passing behavioral evidence. Apply the latest explicit requirements when revocation semantics differ from the historical spec.
- AUD-005: Before testing an invariant, check it against every later requirements file. If a later requirement makes it false, restate it in the spec in the same change. Never name a test after an invariant unless the test would fail when that invariant is broken.
- AUD-006: A stored `issuer` or owner field is not proof of authority. Test every role path that touches it (grant, revoke, renounce, hand-over) and any state, such as escrowed tokens, that becomes unrecoverable when the role is gone.
- AUD-007: "No `receive`/`fallback`" does not mean "cannot receive ETH": `selfdestruct` and coinbase rewards force it in. For every contract that holds ETH, test forced ETH, and provide a way to recover any balance above what is owed.
- AUD-008: Implement each function against both the §5 function table and the §3 roles table. A role restriction stated only in §3 is still a revert condition.
- AUD-006, AUD-007: Write a regression's behaviour assertion first and await it (e.g. `await expect(tx).to.revert(ethers)`), then assert the error name. A test that fails only because an error or function is missing from the ABI does not show a behavioural failure, and an un-awaited transaction can leak into the next test.
